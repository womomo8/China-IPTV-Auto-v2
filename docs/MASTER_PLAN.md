一、项目总目标

China-IPTV-Auto V3 的核心目标：

自动发现、筛选和验证真正能够在中国大陆网络环境下播放的 IPv4 直播源，并持续生成一份可靠、可用的 IPTV 订阅。

项目不以采集数量为目标，而以最终可用线路的真实性和稳定性为目标。

建设原则：

1. 采集范围尽可能广，但不降低最终发布标准。
2. 允许大量线路在筛选过程中被淘汰。
3. 不为追求订阅数量而保留未经验证的线路。
4. 所有测试必须区分网络可连接、媒体可读取和实际播放验证。
5. 优先满足中国移动宽带使用需求。
6. 不同运营商的测试资格必须分别判断，不混合冒充。
7. 整体程序保持轻量、清晰、自动化，避免重复功能和复杂的数据管理。
8. 以真实运行结果为依据，不以代码写完或工作流运行成功代替线路验证。

最终交付目标：

- 能够自动发现多个来源的 IPTV 线路。
- 能够自动整理、去重和筛选。
- 能够识别无效线路和无法读取的媒体流。
- 能够在具备真实国内网络测试条件时验证国内播放资格。
- 能够自动生成并校验正式 M3U 订阅。
- 能够通过 GitHub Actions 定时运行和维护订阅。
- 运行失败时保护已有可用订阅，不发布未经验证的结果。

三、V3 总体建设路线

项目按照以下六个阶段逐步建设。

第一阶段：广泛发现

建立多来源直播源发现机制，尽可能扩大有效候选线路的来源范围。

第二阶段：数据整理

统一数据格式，处理重复 URL、无效地址和 IPv4 准入问题。

第三阶段：快速筛选

使用轻量检测淘汰明显无效、无法连接或不符合基本条件的线路。

第四阶段：深度验证

使用媒体探测和实际读取、解码等方式，验证线路是否真正提供有效媒体内容。

第五阶段：国内网络实测

在真实中国大陆网络环境中进行 IPv4 实测，识别实际出口运营商，判断线路是否具备相应运营商的播放资格。

第六阶段：安全发布

只发布满足正式资格要求的线路，生成订阅文件并进行发布前检查，保护已有可用订阅。

六个阶段必须按照 "CORE_FLOW.md" 规定的顺序执行。

不得因为某个阶段暂时无法实现，就直接跳过验收要求，把未经验证的线路发布到正式订阅。

四、各阶段具体施工计划

阶段一：广泛发现

建设目标

建立可靠的多来源采集系统，持续发现 IPTV 候选线路。

施工任务

1. 建立统一的来源管理方式。
2. 接入公开发现渠道。
3. 支持人工维护的订阅源。
4. 支持多来源同时采集。
5. 对每个来源设置合理的超时和资源限制。
6. 单个来源发生错误时，不影响其他来源继续运行。
7. 对采集失败的来源进行有限重试。
8. 记录本轮采集的基本结果。
9. 防止单个异常来源拖垮整个采集任务。

人工订阅源管理要求

- 人工维护的订阅源保存在统一配置位置。
- 每次运行都重新读取当前配置。
- 不能只在第一次运行时读取一次。
- 某个来源本轮失效，不自动从配置中删除。
- 失败后进行有限重试，仍失败则跳过本轮。
- 后续运行继续尝试该来源。
- 不擅自自动替换人工配置的来源。

阶段输出

本轮发现的原始候选线路。

验收条件

- 多个来源能够正常采集。
- 单个来源失败不会导致整个流程中断。
- 人工订阅源能够在后续运行中重新读取。
- 采集过程具备超时、数量和资源限制。
- 能够得到本轮原始候选数据。

---

阶段二：数据整理

建设目标

将不同来源的数据整理为统一、可供后续检测的候选线路。

施工任务

1. 解析不同来源的直播源格式。
2. 统一线路数据结构。
3. 清理明显无效的数据。
4. 按 URL 去重。
5. 同一频道的不同 URL 不直接合并。
6. 保留后续检测所需的请求头等必要信息。
7. 执行 IPv4 准入检查。
8. 对无法判断或存在异常的数据进行隔离处理。
9. 形成独立的本轮候选数据。

数据管理要求

- 每轮运行以本轮采集的数据为处理对象。
- 不将历史运行数据混入本轮候选。
- 不建立不必要的复杂历史关系。
- 不为简单筛选引入复杂评分、线路关系和数据追踪系统。
- 保留后续验证真正需要的信息。

阶段输出

格式统一、URL 去重并通过基础准入检查的候选线路。

验收条件

- 不同来源能够统一解析。
- 重复 URL 能够正确去除。
- 不同 URL 的同频道线路能够分别保留。
- IPv4 准入结果明确。
- 候选数据能够正常交给下一阶段。

---

阶段三：快速筛选

建设目标

使用低成本检测，尽早淘汰明显不可用的线路，减少后续深度验证的资源消耗。

施工任务

1. 检查基本网络连接情况。
2. 检查必要的 HTTP 响应或媒体连接状态。
3. 检查超时、连接失败等明显异常。
4. 对候选线路进行基础筛选。
5. 设置合理的并发、超时和资源限制。
6. 将检测结果分类传递给深度验证阶段。

筛选原则

- 只做必要的轻量检测。
- 不建设复杂评分系统。
- 不把基础连接成功当成实际播放成功。
- 不因一次暂时性网络错误就永久删除来源。
- 不让低成本检测承担深度媒体验证的职责。

阶段输出

通过基础筛选、值得进一步验证的候选线路。

验收条件

- 明显无效线路能够被淘汰。
- 基础检测结果能够正确分类。
- 检测资源和运行时间可控。
- 通过的线路能够进入深度验证。
- 不把基础检测通过标记为正式可播放。

---

阶段四：深度验证

建设目标

确认候选线路是否真正提供有效的直播媒体内容。

施工任务

1. 使用 FFprobe 探测媒体流信息。
2. 检查是否存在有效的视频或音频流。
3. 使用 FFmpeg 进行实际媒体读取或解码验证。
4. 检查媒体读取是否持续正常。
5. 识别明显异常的媒体内容。
6. 按需要检查广告占位、错误页面等非正常直播内容。
7. 区分线路失败、检测节点故障和无法确定的结果。
8. 将结果传递给国内网络实测阶段。

结果分类

统一使用明确的检测状态：

- "PASS"：本阶段验证通过。
- "FAIL"：本阶段验证失败。
- "UNKNOWN"：无法确定结果。
- "NODE_ERROR"：检测节点或检测环境发生故障。

处理要求

- "UNKNOWN" 不能当成通过。
- "NODE_ERROR" 不能直接判定为线路本身失效。
- 深度验证通过不代表国内网络已经验证通过。
- 不能仅凭频道名称或播放列表文字判断线路真实有效。

阶段输出

通过深度媒体验证的候选线路及其检测结果。

验收条件

- 能够识别有效媒体流。
- 能够发现明显无效或异常内容。
- 能够区分线路故障和检测环境故障。
- 未确定的线路不会被误判为通过。
- 检测结果能够交给国内实测阶段。

---

阶段五：国内网络实测

建设目标

确认线路是否真正能够在中国大陆网络环境下通过 IPv4 播放验证。

这是本项目判断国内可用性的关键阶段。

施工任务

1. 确定真实位于中国大陆的测试环境。
2. 确认测试使用 IPv4 网络。
3. 确认测试节点实际出口网络和运营商。
4. 对候选线路进行真实媒体读取和解码。
5. 判断线路是否通过相应运营商的验证。
6. 将不同运营商的结果分开处理。
7. 记录本轮真实测试结果。
8. 将满足正式资格要求的线路交给发布阶段。

运营商资格要求

- 中国移动测试通过，只能证明线路通过相应移动测试环境的验证。
- 不能据此宣称联通、电信也通过。
- 不同运营商的测试结果不能混合冒充。
- 项目优先满足中国移动宽带使用需求。
- 正式订阅按照已经确认的运营商发布策略执行。

国内实测环境要求

海外 GitHub Actions Runner 不能冒充中国大陆网络实测。

如果当前没有真实国内测试环境：

- 如实标记国内实测尚未完成。
- 不得将海外测试结果当成国内通过。
- 不得将尚未取得国内实测资格的线路冒充正式合格线路。
- 继续保留该阶段的实施任务，待具备条件后再完成。

阶段输出

具有明确国内 IPv4 测试结果和运营商资格的线路。

验收条件

- 测试节点真实位于中国大陆。
- 测试使用 IPv4。
- 实际出口运营商能够确认。
- 线路经过真实媒体读取或解码验证。
- 不同运营商资格分别判断。
- 测试结果明确且可用于正式发布判断。

阶段六：安全发布

建设目标

将符合正式发布资格的线路生成稳定订阅，并通过 GitHub 仓库固定路径持续提供。

正式订阅位置

"output/iptv.m3u"

施工任务

1. 接收国内实测阶段符合发布资格的线路。
2. 生成临时 M3U 文件。
3. 检查 M3U 格式和内容。
4. 检查频道数据和线路地址。
5. 检查发布结果是否符合正式资格要求。
6. 通过后再替换正式订阅文件。
7. 由 GitHub Actions 完成正式 Git 提交和推送。
8. 保存必要的运行日志和结果。
9. 发布失败时保护原有正式订阅。

发布保护要求

以下情况不得覆盖已有正式订阅：

- 本轮没有有效线路。
- 本轮全部线路未通过正式资格要求。
- 国内实测阶段没有取得所需结果。
- 出现全局检测节点故障。
- 临时订阅格式或内容校验失败。
- 正式发布过程失败。

不得为了让订阅文件保持更新而发布未经验证的线路。

阶段输出

经过资格检查和格式校验的正式 IPTV 订阅：

"output/iptv.m3u"

验收条件

- 临时文件生成正常。
- 发布前校验正常。
- 不合格线路不会进入正式订阅。
- 发布失败时旧订阅得到保护。
- 正式文件更新结果能够确认。
- GitHub Actions 只有在实际提交成功后才能报告发布成功。

五、程序结构建设计划

程序结构必须服从 "CORE_FLOW.md"。

目前确定的主要职责如下：

文件或目录| 主要职责
"main.yml"| GitHub Actions 调度、环境准备、权限管理和正式 Git 提交
"pipeline.py"| 唯一业务入口，按总流程组织各阶段
"settings.py"| 统一管理参数、阈值、超时、并发和资源预算
"sources.txt"| 管理人工订阅源和公开发现入口
"discovery.py"| 多来源采集
"normalize.py"| 数据解析、统一、去重和 IPv4 准入
"validator.py"| 基础检测、深度验证和国内实测结果处理
"publisher.py"| 临时 M3U 生成、发布前校验和正式文件准备
"tests/"| 各模块和整体流程测试
"output/iptv.m3u"| 正式订阅文件

以上是当前确认的核心结构。实际编码前必须核对仓库现状及 "CORE_FLOW.md" 中的具体定义。

不得仅凭本表就擅自新增或删除程序文件。

5.1 单一业务入口

所有业务阶段统一由 "pipeline.py" 组织。

不能让多个脚本各自形成互相独立的业务入口，造成流程重复、执行顺序混乱。

5.2 调度与业务分离

"main.yml" 负责调度，不负责重复实现业务逻辑。

业务处理统一交给程序入口和相应模块。

5.3 统一配置

运行参数和资源限制集中管理，避免相同参数分散在多个文件中。

5.4 三种运行模式

项目按照总流程支持：

- 自动定时运行。
- 手动正式运行。
- 手动测试运行。

三种模式共享同一套业务逻辑，不得各自维护一套重复流程。

测试模式必须与正式发布隔离：

- 测试任务只使用必要的只读权限。
- 测试任务不得覆盖正式订阅。
- 测试任务不得执行正式 Git 提交和推送。
- 正式任务才执行正式发布。

5.5 定时运行

当前确定的自动运行计划：

每天北京时间 06:00 自动执行。

具体调度配置以 "CORE_FLOW.md" 和实际工作流实现为准。

六、工程开发顺序与阶段验收

开发必须按依赖顺序推进，不能同时随意铺开大量模块。

第一轮：基础工程搭建

任务：

1. 核对仓库目录。
2. 确认核心文件结构。
3. 建立统一配置。
4. 建立唯一业务入口。
5. 建立基础测试结构。
6. 建立 GitHub Actions 调度框架。

验收：

- 项目结构清楚。
- 程序能够启动。
- 入口和配置能够正常工作。
- 测试模式和正式模式权限隔离。
- 没有重复的业务入口。

第二轮：采集和数据整理

任务：

1. 完成来源读取。
2. 完成多来源采集。
3. 完成人工订阅源管理。
4. 完成格式解析。
5. 完成 URL 去重。
6. 完成 IPv4 准入。

验收：

- 能够从多个来源获得候选线路。
- 单个来源失败不影响整体采集。
- 数据能够统一整理。
- 人工来源能够在每轮重新读取。
- 候选数据能够正常进入快速筛选。

第三轮：基础筛选和深度验证

任务：

1. 完成基础连接检测。
2. 完成超时和异常处理。
3. 完成 FFprobe 探测。
4. 完成 FFmpeg 媒体读取或解码。
5. 完成检测状态分类。
6. 完成资源预算控制。

验收：

- 无效线路能够被淘汰。
- 有效媒体流能够得到识别。
- 线路故障和节点故障能够区分。
- 未确定结果不会被当成通过。

七、文件修改与施工纪律

本项目必须执行统一的文件修改制度。

任何 ChatGPT 窗口、任何开发阶段，都必须遵守以下规则。

7.1 修改前先核对真实仓库

开始任何代码施工前：

1. 查看仓库当前文件。
2. 阅读最新版 "CORE_FLOW.md"。
3. 阅读最新版 "MASTER_PLAN.md"。
4. 查看相关程序文件。
5. 检查相关模块之间的调用关系。
6. 确认当前工作进度和已经验收的内容。

不得只凭聊天记录、旧代码或模型记忆直接写代码。

7.2 禁止擅自改变总体方案

未经确认，不得：

- 改变项目最终目标。
- 改变六阶段业务流程。
- 改变已经确认的程序架构。
- 擅自增加复杂评分系统。
- 引入不必要的数据库和历史关系系统。
- 增加与核心目标无关的功能。
- 擅自改变正式订阅发布方式。
- 把海外检测冒充国内实测。

发现现有方案确实有问题时，先提出证据和修改建议，再确定是否修改。

7.3 禁止随意增加或删除文件

新增文件必须说明：

- 为什么需要新增。
- 具体承担什么职责。
- 是否与现有文件功能重复。
- 是否会增加维护成本。
- 是否符合总流程。

删除文件必须说明：

- 文件当前用途。
- 是否有其他模块依赖。
- 删除后是否影响运行。
- 是否已经确认不再需要。

未经确认不得擅自新增、删除或重命名核心文件。

7.4 修改必须考虑上下游影响

不能只修复一个文件，却破坏其他模块。

修改前检查：

- 输入数据是否变化。
- 输出数据是否变化。
- 函数接口是否变化。
- 其他文件是否调用该功能。
- 测试是否需要同步调整。
- 是否影响整体流程和发布安全。

7.5 代码交付要求

代码交付统一采用以下方式：

1. 先说明本次修改的目的。
2. 说明需要修改的文件。
3. 提供 Git Commit 提交说明。
4. 提供完整文件内容。
5. 明确文件上传位置。
6. 说明如何测试。
7. 说明预期通过条件。

重大修改必须提供完整替换文件，不要求用户到处寻找代码片段。

只有非常小且明确的修改，才可以提供局部修改方法。

用户负责将文件上传到 GitHub 并提交。

7.6 不重复建设

如果已有模块能够承担某项职责，就优先修复或扩展现有模块。

不得因为不同窗口或不同开发人员的习惯不同，就重新建立一套相同功能。

已经通过验收的模块，不得随意重写。

确实需要重写时，必须说明原因、影响范围和回归测试要求，并得到确认。

八、测试、问题整改与完成认定

8.1 每批施工都必须有验收标准

不能只以代码写完作为完成标准。

每次修改必须说明：

- 修改了什么。
- 为什么修改。
- 是否符合 "CORE_FLOW.md"。
- 影响哪些文件和模块。
- 如何测试。
- 通过条件是什么。
- 当前测试结果是什么。

8.2 问题整改制度

发现问题后：

1. 明确问题发生在哪个阶段。
2. 确认问题原因。
3. 判断属于代码问题、配置问题、网络问题还是测试环境问题。
4. 评估对上下游的影响。
5. 按照总流程确定整改方案。
6. 修复后进行对应测试。
7. 必要时执行回归测试。
8. 更新工程进度。

不能因为发现一个问题，就不断扩大检查范围，形成没有结束条件的反复诊断。

每次整改都应围绕明确的问题和验收条件完成。

8.3 完成状态必须准确

所有工作必须区分以下状态：

状态| 含义
已确定| 方案已经讨论并确认
已编写| 文件或代码已经提供
已上传| 用户已经上传并提交到仓库
已测试| 已执行对应测试，但结果可能尚未通过
已验收| 测试证据符合预定验收条件
待处理| 尚未完成
受阻| 因环境、权限或外部条件暂时无法继续

不能将“已确定”写成“已实现”。

不能将“已上传”写成“已测试”。

不能将“GitHub Actions 运行成功”写成“国内直播播放成功”。

8.4 测试证据

测试结果必须能够说明：

- 测试对象。
- 测试环境。
- 测试方式。
- 实际结果。
- 是否达到验收标准。

没有实际证据，不得标记为已验收。
