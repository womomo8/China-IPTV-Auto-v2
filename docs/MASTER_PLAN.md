一、文件地位与执行效力

本文件是 China-IPTV-Auto-v2 全仓库一体化自动运行与智能调度整改的最高级别依据。

所有新增功能、代码修改、模块整合、数据库变更、自动化调度、测试验收和正式发布，均必须遵守本方案。

本方案与仓库其他文件的关系：

1. "MASTER_PLAN.md"：规定项目最终目标、整体架构、统一规则、整改顺序和验收标准。
2. "CORE_FLOW.md"：展示整体业务流程、阶段细节和具体运行规则。
3. "config.yaml"：保存实际运行参数。
4. "config/channels.yaml"：保存唯一正式频道目录。
5. "iptv_auto/pipeline.py"：负责统一调度和执行整个业务流程。
6. "data/iptv_auto.sqlite3"：保存所有阶段的统一业务数据。
7. "tests/"：验证代码是否符合本方案。

发生文件之间的规则冲突时，必须先核对本方案并修正文档或代码，不得自行形成第二套标准。

本文件规定的是最终目标和整改要求，不代表所有功能已经实现。每项功能必须经过实际代码核对和测试，才能标记为完成。

二、项目最终目标

建设一个真正完整、统一、高效率、自动运行、能够持续更新的 IPTV 线路发现、筛选、检测、评分和正式发布系统。

最终必须实现：

- 自动发现公开订阅来源。
- 自动采集和解析线路。
- 自动识别38个正式频道。
- 自动完成线路初筛和准入。
- 自动完成基础测速和综合评分。
- 自动选择优质候选线路。
- 自动进行深度检测。
- 自动进行内容检查。
- 自动进行稳定性复测。
- 自动识别和标记真实网络出口。
- 自动完成发布资格审核。
- 自动生成正式订阅。
- 自动安全更新和备份。
- 自动记录任务进度。
- 中断后能够从原任务恢复。
- 每个阶段达到条件后自动停止并交接下一阶段。

最终架构必须坚持：

一个主仓库、一条自动化主流程、一个主程序入口、一套统一数据库、一份正式频道目录、一份统一配置、一套质量标准、一个正式发布出口。

允许分阶段施工，但不允许最终形成多个相互独立、需要人工协调的业务系统。

三、正式频道统一标准

唯一正式频道目录：

"config/channels.yaml"

正式频道总数：38个。

频道分类| 数量
央视频道| 10
卫视频道| 12
港澳台频道| 5
体育频道| 11
合计| 38

必须遵守以下规则：

1. 38个频道是正式频道总目录。
2. 每个频道具有唯一、稳定的 "channel_id"。
3. 每个频道只能归属一个正式分类。
4. 来源中的频道名称和分类变化不得改变正式频道身份。
5. 不在正式目录中的频道不得自动成为正式发布目标。
6. 未经确认不得新增、删除或合并正式频道。
7. CCTV-5 与 CCTV-5+ 是两个独立频道。
8. NBA TV、ESPN、Sky Sport Basket、beIN SPORTS NBA、TNT Sports 4 保留在体育频道。
9. NBC Sports 不列入当前正式频道目录。
10. 频道目录发生错误时，必须停止后续正式处理和发布。

所有模块统一读取正式频道目录，不允许分别维护自己的正式频道名单。

五、统一自动化业务主流程

最终业务主流程：

启动任务

→ 创建唯一 run_id

→ 读取统一配置

→ 校验38个正式频道

→ 检查统一数据库

→ 恢复或创建本轮任务

→ 自动发现公开来源

→ 采集和解析订阅

→ 标准化线路

→ 正式频道匹配

→ IPv4准入筛选

→ 无效线路和黑名单过滤

→ 线路登记

→ 固定本轮候选名单

→ 基础测速

→ 统一评分

→ 优质候选筛选

→ 深度检测

→ 内容检查

→ 稳定性复测

→ 网络出口验证

→ 发布资格审核

→ 生成临时订阅

→ 发布前检查

→ 原子更新正式订阅

→ 保存运行报告

→ 结束本轮任务。

所有阶段使用同一个 "run_id"。

任何模块不得自行创建与主流程无关的业务任务。

六、统一候选名单和数据范围

这是全仓库必须优先解决的核心问题。

每一轮任务必须形成独立、固定、可恢复的候选名单。

候选名单必须明确记录：

- "run_id"
- "line_id"
- "channel_id"
- 来源身份
- 准入时间
- 准入结果
- 拒绝原因（如有）

候选名单以线路与正式频道的配对关系为基础。

同一条线路对应多个频道时，必须保留各自的频道配对关系。

同时区分：

- 线路级数据：测速、线路综合评分等。
- 频道配对级数据：频道匹配、频道内容、频道候选资格等。

不能因为线路级记录只保存一次，就丢失同一线路对应的其他频道关系。

每轮候选上限暂按现有统一配置36执行。

必须在整改中明确36的统计口径，统一候选条目、线路数量和线路频道配对数量的定义，不能混用。

候选名单一经本轮准入完成，就必须固定并供下游所有阶段使用。

下游模块只能处理本轮已准入的数据，不得重新读取全历史线路后扩大候选范围。

特别禁止：

1. 基础测速重新从全历史线路中挑选候选。
2. 评分把其他运行任务的历史线路混入本轮。
3. 深度检测扩大本轮候选范围。
4. 内容检查使用不属于本轮的频道配对。
5. 稳定性复测绕过本轮准入名单。
6. 任务恢复时重新采集并改变原候选名单。

历史数据可以参与有明确依据的来源可靠性评估，但不能因此自动成为本轮候选。

七、统一阶段调度、停止与交接机制

这是本次整改必须正式建设的核心功能。

不另外建立一套独立调度系统，直接由：

"iptv_auto/pipeline.py"

统一负责所有阶段的调度。

每个阶段必须定义：

1. 输入条件。
2. 执行任务。
3. 完成条件。
4. 正常停止条件。
5. 失败条件。
6. 超时条件。
7. 重试规则。
8. 输出数据。
9. 下一阶段交接条件。
10. 中断恢复规则。

7.1 统一阶段状态

统一使用以下状态：

状态| 含义
"pending"| 等待执行
"running"| 正在执行
"completed"| 正常完成
"completed_no_candidates"| 正常完成，但没有合格候选
"failed"| 执行失败
"timeout"| 达到时间上限
"skipped"| 根据明确条件跳过

状态必须保存在统一任务记录中。

7.2 五种统一停止情况

停止原因| 系统动作
达到目标数量| 正常停止并交接下一阶段
所有候选处理完成| 正常结束并交接结果
超过时间限制| 保存进度，按恢复规则处理
暂时性网络故障| 按次数上限重试
数据错误或关键条件不满足| 停止下游并记录失败原因

必须区分：

停止当前阶段，不等于停止整个任务。

例如：

- 基础测速完成三轮，停止测速并进入评分。
- 评分完成，停止评分并进入深度检测。
- 深度检测完成，进入内容检查。
- 所有发布条件满足，才允许进入正式发布。

7.3 自动交接规则

上游阶段必须先完成必要工作、保存数据、确认结果，再允许下游阶段执行。

任何阶段失败时，不得把不完整结果当成合格结果交给下游。

零候选时应正常结束本轮，不得继续执行没有意义的测速和深度检测。

阶段超时必须记录原因和已完成进度，不得直接把超时结果认定为成功。

7.4 重试规则

网络暂时性故障可以有限重试。

数据结构错误、频道身份错误、数据库关键错误和必要条件缺失，不允许无限重试。

重试必须记录次数、原因和结果。

不得通过无限循环或无限请求来掩盖失败。

八、统一任务恢复机制

任务恢复与阶段调度必须一起建设。

恢复任务时：

1. 读取原 "run_id"。
2. 读取原候选名单。
3. 读取原阶段状态。
4. 读取已经完成的阶段结果。
5. 识别当前中断阶段。
6. 从符合恢复条件的位置继续执行。

必须保证：

- 不重新发现已完成的来源。
- 不重新建立不同的候选名单。
- 不重复完成已经确认成功的阶段。
- 不丢失已经完成的检测结果。
- 不把其他任务的历史结果当成本轮结果。
- 不因恢复操作改变原候选范围。

如果某个阶段内部存在未完成的任务，应优先沿用已有的任务预留和恢复机制。

恢复时必须校验 "run_id"、执行环境和任务身份。

无法安全恢复时，应停止并报告原因，不得擅自重新开始一轮伪装成原任务。

九、各业务阶段执行标准

第一阶段：公开来源发现与线路初筛

执行内容：

1. 自动发现公开订阅来源。
2. 来源池容量30个。
3. 每轮最多新增发现来源8个。
4. 第一阶段最长运行时间480秒。
5. 单次网络请求超时8秒。
6. 支持统一配置中的人工来源。
7. 采集并解析支持的订阅格式。
8. 标准化线路和频道名称。
9. 匹配38个正式频道。
10. 执行IPv4前置准入。
11. 过滤空地址、占位地址、明显无效地址。
12. 执行黑名单检查和去重。
13. 保存来源历史和线路关系。
14. 形成固定本轮候选名单。

完成条件：

- 已安排来源处理完成，或达到明确停止条件。
- 来源检查结果已保存。
- 候选线路和频道配对已保存。
- 准入和拒绝统计已保存。

无候选时：

记录 "completed_no_candidates"，结束本轮。

第二阶段：基础测速

统一配置：

- 基础测速三轮。
- 单次测速超时8秒。
- 最大并发12。

每轮必须记录真实检测结果。

测速按线路级执行，避免同一条线路仅因关联多个频道而重复进行相同基础测速。

完成条件：

- 本轮需要测速的线路完成规定轮次。
- 结果已写入统一数据库。
- 未完成任务已记录原因。
- 下游可以读取本轮准确结果。

第三阶段：统一评分

统一评分权重：

评分项目| 权重
成功率| 30
稳定性| 25
吞吐能力| 15
新鲜度| 15
广告占位风险| 10
来源可靠性| 5
合计| 100

质量等级：

- A级：85分及以上。
- B级：70至84分。
- C级：50至69分。
- 低于50分：不进入优质候选池。

评分必须基于真实数据。

评分时严格限定本轮线路和频道配对。

第四阶段：深度检测

统一要求：

- 每个正式频道最多选取5条优质候选。
- 使用FFmpeg、FFprobe进行检测。
- 深度检测单次超时25秒。
- 检查线路实际可用性。
- 记录检测证据和失败原因。

必须保留一条线路关联多个频道时的频道配对信息。

不得因线路级检测结果只保存一次，就丢失其他频道的候选身份。

第五阶段：内容检查

检查内容：

- 实际播放内容是否与正式频道匹配。
- 是否存在广告占位。
- 是否存在明显错误画面。
- 是否存在空画面或无效内容。

只有本轮深度检测合格的候选，才可以进入相应内容检查。

确认广告占位和确认无效内容，可以按照规则处理。

临时网络异常不得直接永久拉黑。

第六阶段：稳定性复测

统一配置：

- 最多两轮复测。

只处理本轮已经通过必要前置检查的候选。

复测必须记录：

- 线路身份。
- 频道配对。
- 本轮运行标识。
- 复测轮次。
- 成功或失败状态。
- 响应情况。
- 失败原因。

卡顿、拥堵和短暂断流主要影响质量评价，不应直接等同于永久失效。

第七阶段：网络出口验证

必须明确区分：

1. 云端检测出口。
2. 国内真实IPv4出口。
3. 福建移动真实家庭网络出口。

云端测试不能冒充国内家庭网络测试。

其他运营商不能冒充福建移动。

没有真实福建移动出口检测条件时，必须标记为未验证。

所有网络身份结论必须有真实检测依据。

第八阶段：正式发布

发布条件：

1. 最近一次测量成功。
2. 满足三轮基础测速要求。
3. 成功率不低于90%。
4. 综合评分不低于70。
5. FFprobe检测通过。
6. 频道内容符合正式目录。
7. 不存在确认的广告占位和无效内容。
8. 网络出口身份如实标记。
9. 每个频道最多保留3条正式线路。
10. 发布文件通过完整检查。

正式发布流程：

生成临时文件

→ 检查格式

→ 检查频道身份

→ 检查线路有效性

→ 检查发布数量

→ 全部通过

→ 原子更新正式文件

→ 保存备份和发布记录。

正式发布出口：

"output/result.m3u"

备份目录：

"output/backups/"

发布失败时必须保留上一版有效订阅。

未经完整检查，不得覆盖旧版正式订阅。

十、统一数据库与历史数据保护

唯一数据库：

"data/iptv_auto.sqlite3"

所有阶段使用统一数据库。

数据库负责保存：

- 运行记录。
- 阶段状态和进度。
- 来源信息和来源历史。
- 线路身份。
- 正式频道身份。
- 线路与频道关系。
- 候选准入名单。
- 基础测速记录。
- 评分记录。
- 深度检测记录。
- 内容检查记录。
- 稳定性复测记录。
- 网络出口验证记录。
- 黑名单记录。
- 正式发布记录。

历史数据保护是强制要求。

禁止：

1. 为了测试方便清空整个数据库。
2. 删除历史线路记录来解决候选范围问题。
3. 擅自删除来源历史。
4. 用新数据库覆盖旧数据库。
5. 通过重建数据库掩盖程序错误。

如确实需要数据库结构升级，必须使用兼容迁移，并验证原有数据完整保留。

优先复用现有数据库字段和运行记录，避免不必要的结构变更。

十一、全仓库整改与施工顺序

所有整改以最终一体化运行为目标。

按照以下八个阶段依次施工。

第一阶段：整体基准核对与统一架构固定

1. 核对仓库文件结构。
2. 核对正式频道目录。
3. 核对统一配置。
4. 核对唯一主流程入口。
5. 核对数据库结构。
6. 核对自动化启动器。
7. 定位真实正式发布模块。
8. 核对相关单元测试和集成测试。
9. 建立本总方案与现有文档的统一关系。

第二阶段：候选名单统一与线路身份统一

1. 统一本轮候选名单。
2. 明确36条候选上限的统计口径。
3. 保留线路与频道配对关系。
4. 增加真实准入结果记录。
5. 固定本轮候选范围。
6. 阻止下游模块读取全历史数据扩大候选。
7. 保留线路级测量和评分的数据结构。
8. 增加候选范围相关测试。

第三阶段：基础测速和统一评分

1. 基础测速只读取本轮准入线路。
2. 三轮测速规则统一。
3. 测速结果关联统一运行标识。
4. 评分只使用本轮线路。
5. 频道候选只使用本轮频道配对。
6. 完成相关测试。

第四阶段：深度检测、内容检查和稳定性复测

1. 深度检测严格限定本轮候选。
2. 每频道最多5条候选。
3. 保留多频道线路配对关系。
4. 内容检查严格限定本轮候选。

十二、统一测试和验收规则

每次整改必须执行：

1. 先读取GitHub主分支真实源代码。
2. 先核对调用关系和数据结构。
3. 确认问题后再确定修改范围。

9. 再运行相关集成测试。
10. 最后运行全仓库测试。

- 旧版订阅保留。
- 数据库历史记录保护。

十三、GitHub自动运行规则

GitHub Actions只能作为统一主程序的启动入口。

必须保持：

- 一个统一workflow入口。
- 一个统一主程序。
- 一套统一运行参数。
- 一套统一数据库。
- 一份统一运行报告。

不得通过多个独立workflow分别完成不同业务阶段，再要求人工协调结果。

定时任务目前保持暂停。

只有在整体整改、集成测试和发布验收通过，并得到用户明确确认后，才能恢复定时自动运行。

十五、每次开发和整改的强制工作方式
