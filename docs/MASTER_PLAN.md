China-IPTV-Auto V3 MASTER PLAN

自动化运营系统施工总计划

设计版本：2026-11-05

施工原则：以 CORE_FLOW.md 为唯一业务流程依据。

---

一、施工总目标

将现有 China-IPTV-Auto V3 整理为一套精简、统一、可恢复、可自动运行的 IPTV 质量筛选系统。

不推倒重建。

不另起一套 V4。

不重复建立数据库。

不随意增加独立入口。

所有修改以现有 V3 真实代码为基础，优先整改错误和不完整功能。

最终目标：

从大量公开来源中发现线路，通过五层质量筛选，获得真正经过国内 IPv4 网络验证的直播源，并安全更新订阅。

---

二、工程统一规则

2.1 唯一数据库

"data/iptv_auto.sqlite3"

全部业务模块共享同一数据库。

禁止：

- 建立第二套业务数据库。
- 各模块独立保存互不关联的业务状态。
- 通过临时文件代替正式数据库状态。
- 重复保存同一业务数据。

2.2 唯一主入口

"iptv_auto/pipeline.py"

所有业务阶段由唯一主入口统一调度。

禁止：

- 各阶段独立启动正式任务。
- 重复建立第二套主流程。
- 绕过统一候选池直接执行下游检测。
- 绕过发布审核直接更新正式订阅。

2.3 统一运行标识

每次运行生成唯一 "run_id"。

所有来源、候选、测量、检测、国内实测和发布记录必须能够关联到对应任务。

2.4 统一配置

- "config.yaml"：系统参数和资源预算。
- "config/channels.yaml"：频道目录。
- 不允许同一业务参数在多个配置文件中重复定义。
- 关键配置变更必须影响任务恢复的一致性判断。

三、五层施工计划

第一阶段：第一层——广泛发现

施工目标

建立完整、多来源、可恢复的候选发现机制。

保留和整改

1. 保留现有来源发现模块。
2. 保留现有 M3U、M3U8、TXT 解析能力。
3. 保留频道名称标准化。
4. 保留线路与频道配对关系。
5. 保留多来源去重。
6. 保留 IPv4 初步准入。

必须整改

1. 来源发现不能过度依赖单一来源渠道。
2. 来源采集进度必须持久化。
3. 每个来源必须记录处理状态。
4. 记录来源请求失败和超时。
5. 保留线路的多个来源出处。
6. 统一线路与频道配对身份。
7. 取消快速测速前固定36条候选的过早限制。
8. 修复采集超时后仍提前冻结候选的问题。

候选池规则

- 采集期间允许持续增加候选。
- 不因某一个来源失败就停止其他来源。
- 所有计划来源完成后统一汇总。
- 来源超时未完成时保存进度，不冻结。
- 候选汇总完成后生成不可变快照。
- 冻结后下游只能处理该快照中的对象。

验收标准

- 多来源能够正常采集。
- 重复线路能够正确去重。
- 多来源出处得到保留。
- IPv4 初步准入正确。
- 超时不会错误冻结。
- 所有来源完成后才能冻结。
- 冻结名单能够准确复现。

---

第二阶段：第二层——快速淘汰

施工目标

使用较低成本的检测，尽早排除明显不合格线路。

保留功能

- 协议检查。
- 基础连接测试。
- 多轮测速。
- 延迟记录。
- 吞吐量测量。
- 质量评分。
- 候选排序。

必须整改

1. 测速模块必须读取本轮冻结候选。
2. 评分模块必须读取本轮测速结果。
3. 禁止遍历全数据库历史线路参与本轮评分。
4. 硬性准入与评分分离。
5. 不合格线路不得通过高评分进入下一阶段。
6. 暂时性网络失败与永久失效分开处理。
7. 测速次数和并发量受统一资源预算控制。

评分原则

评分只负责比较通过硬性条件的候选。

评分不能替代：

- IPv4 准入。
- 实际连接验证。
- 频道正确性。
- 广告检测。
- 国内真实播放。

验收标准

- 只处理本轮冻结候选。
- 不读取其他运行的历史候选。
- 测速结果能够关联线路和频道。
- 评分排序正确。
- 失败状态准确。
- 重复运行不会产生错误数据覆盖。

---

第三阶段：第三层——深度验证

施工目标

确认线路是否真正提供有效的电视直播内容。

A. FFprobe

- 检查媒体流。
- 检查视频编码。
- 检查音频编码。
- 检查分辨率。
- 检查帧率。
- 检查媒体流持续输出。

B. FFmpeg

- 视频解码验证。
- 视频帧抽样。
- 黑屏检测所需图像提取。
- 必要的视频内容分析。

C. 频道内容验证

- 识别频道标识。
- 检查频道是否串台。
- 检查实际内容是否符合频道声明。
- 不能仅凭 URL 名称判定频道正确。

D. 广告和占位检测

- 广告画面。
- 广告关键词。
- 无信号画面。
- 静态占位画面。
- 黑屏。
- 错误页面。

E. 稳定性

- 连续播放。
- 首帧时间。
- 播放中断。
- 超时。
- 码流异常。
- 有限复测。

必须整改

1. 深度检测严格限定本轮候选。
2. 内容检查必须使用线路与频道配对结果。
3. 充分利用数据库中的 "run_candidate_checks"。
4. 检测结果不能只保存在无结构的 JSON 中。
5. 统一淘汰原因。
6. 不允许 FFprobe 成功就直接认定频道正确。
7. 稳定性复测必须有明确次数和时间上限。

验收标准

每个深度候选必须有完整检测结果。

不能只有一个简单的 PASS。

---

第四阶段：第四层——国内网络实测

施工目标

建立真实国内 IPv4 网络播放验证能力。

这是项目最重要的最终质量关卡。

必须建设

1. 国内真实 IPv4 测试节点。
2. 运营商识别。
3. 实际 IPv4 出口验证。
4. 真实播放测试。
5. 首帧时间检测。
6. 连续播放时长检测。
7. 中断次数检测。
8. 播放内容检查。
9. 运营商适用范围记录。

测试分类

- 中国移动。
- 中国联通。
- 中国电信。

重要规则

1. 云端测速不能代替国内实测。
2. DNS 返回 IPv4 不能代替真实 IPv4 连接。
3. 只有移动通过，不能标记为三网通用。
4. 测试节点故障不能直接判定线路失效。
5. 没有测试证据的线路必须标记 UNVERIFIED。
6. 不得将未验证线路混入正式发布。

验收标准

国内测试必须有真实测试节点、真实出口证据和实际播放结果。

在没有国内节点之前，第四层不得标记完成。

---

第五阶段：第五层——安全发布

施工目标

只将符合质量标准的线路生成正式订阅。

必须建设

1. 最终质量资格审核。
2. 运营商适用范围判断。
3. 合格频道整理。
4. M3U 生成。
5. TXT 生成（如配置需要）。
6. 文件格式验证。
7. 内容完整性检查。
8. SHA-256 校验。
9. 上一版本自动备份。
10. 原子替换。
11. 失败保护。
12. 版本记录。
13. 发布历史保存。

发布原则

- 只有通过全部对应门槛的线路才能发布。
- 38个频道是目标目录，不是强制填充数量。
- 不合格线路不准降级混入。
- 新版本校验失败不得替换旧版本。
- 正式发布必须能够追溯对应 "run_id"。

验收标准

模拟发布成功、发布失败、文件损坏和备份恢复，均必须得到正确结果。

四、基础设施整改计划

五层业务之外，必须完善以下基础能力。

4.1 数据库

保留现有 V3 SQLite 数据库。

检查：

- 表结构。
- 外键关系。
- 唯一索引。
- 状态字段。
- 事务。
- 并发写入。
- WAL checkpoint。
- 数据库完整性。
- 任务关联关系。

优先补齐现有表，不随意创建重复表。

4.2 断点恢复

必须使用：

- "runs"
- "run_stages"
- "source_checks"
- "run_candidate_pool"
- "run_candidates"

完成真正的阶段状态管理。

规则：

1. 任务启动时生成 "run_id"。
2. 每个阶段开始前记录状态。
3. 阶段结束后持久化结果。
4. 已完成阶段恢复时跳过。
5. 未完成阶段只处理未完成对象。
6. 候选快照恢复时验证一致性。
7. 配置摘要变化时按规则阻止错误续跑。
8. 失败任务支持有限重试。
9. 不允许跨运行混用候选结果。

4.3 自动调度和资源保护

统一配置：

- 来源处理超时。
- 单任务超时。
- 阶段超时。
- 全局运行预算。
- 并发数量。
- 最大重试次数。
- 数据库操作超时。
- 网络请求超时。

禁止无限循环。

4.4 GitHub Actions

完善：

- 首次运行数据库初始化。
- 历史数据库 Artifact 恢复。
- 恢复来源验证。
- SQLite 完整性检查。
- 数据库保存。
- 运行失败状态记录。
- 任务恢复入口。
- 正式订阅发布。
- 发布 Artifact 保存。

七、验收制度

每个批次必须提供：

1. 修改文件清单。
2. 修改原因。
3. 关联模块。
4. 测试方法。
5. 实际测试结果。
6. 未解决问题。
7. 下一批施工范围。

状态只允许：

- NOT_STARTED：未开始。
- IN_PROGRESS：施工中。
- BLOCKED：受阻。
- TESTING：测试中。
- PASSED：验收通过。
- FAILED：验收失败。

没有测试证据，不允许标记 PASSED。

已经通过验收的模块不随意重写。
