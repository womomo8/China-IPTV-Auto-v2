# China-IPTV-Auto：全仓库整改总方案

- 版本：V3.0
- 日期：2026-11-05
- 仓库：`womomo8/China-IPTV-Auto-v2`
- **业务流程唯一准则：`docs/CORE_FLOW.md`**
- 本文件只规定项目治理、施工顺序、文件管理、测试与验收；不得复制或另立业务规则。

## 一、建设目标

将仓库整理成一套精简、统一、可持续运行的 IPTV 自动发现、采集、筛选、检测、评分、复测、网络身份验证和安全发布系统。

固定架构：

- 一个主仓库；
- 一条业务主流程；
- 一个入口 `iptv_auto/pipeline.py`；
- 一个数据库 `data/iptv_auto.sqlite3`；
- 一份运行配置 `config.yaml`；
- 一份38频道目录 `config/channels.yaml`；
- 一个正式订阅出口 `output/result.m3u`；
- 一个GitHub Actions启动器。

所有业务规则以 `docs/CORE_FLOW.md` 为准。任何文件与其冲突，修正文件，不迁就旧代码。

## 二、数据政策

1. 不再开发V1/V2历史数据库迁移，不保留为旧版本服务的迁移逻辑和迁移专用测试。
2. V3从全新数据库开始。切换时明确废弃旧数据库Artifact，首次运行创建全新结构。
3. 新系统运行后必须持续复用同一个V3数据库，不能每轮创建空库。
4. 只保留新系统正常运行需要的数据：来源池、来源检查、运行记录、候选池、冻结候选、阶段状态、检测结果、黑名单和发布记录。
5. 不把旧历史业务数据带入新系统；不把“每轮运行数据”误删为旧数据。
6. GitHub Actions临时机器需要跨运行恢复/保存唯一数据库文件。Artifact只作为数据库持久化载体，不是第二数据库。
7. 正式订阅备份属于发布安全保护，不属于需要清理的旧业务数据。

## 三、施工顺序

### 第0批：冻结施工基准（当前批次）

- 用V3总流程图替换旧版简短原则文件。
- 将MASTER_PLAN改为治理/验收文件，所有业务细节指向CORE_FLOW。
- 统一README的版本、数据政策和流程入口。
- 固定38频道目录，不在本批擅自改频道。

### 第1批：全仓库文件和依赖核查

- 建立完整文件清单。
- 对每个Python模块确认调用者、被调用者、配置项、数据库表和测试。
- 检查所有文件是否在主流程或测试中实际使用。
- 标记为：保留、合并、删除、待验证。
- 只有确认无调用、无配置引用、无数据依赖、无测试价值的文件才删除。
- 不按文件名猜测是否过时，不为了“精简”删掉必要模块。

### 第2批：全新V3数据库和候选/阶段骨架

- 以全新V3 schema初始化，不含V1/V2迁移。
- 增加候选池、候选池来源关系、冻结名单、冻结名单来源关系、频道配对检查记录。
- 所有阶段统一 `run_id` 和状态记录。
- 第一阶段完成所有来源采集后统一筛选冻结，明确36是频道配对上限。
- 同批实现来源级断点恢复和冻结名单不可变。
- 测试多来源去重、来源公平性、候选数量统计、恢复和冻结保护。

### 第3批：下游候选范围统一

- 基础测速只测本轮冻结候选对应的物理线路。
- 评分只评本轮测量结果，频道配对只从冻结名单产生。
- 深度检测保留线路级复用，但不冒充频道内容匹配。
- 内容检查按线路/频道配对分别保存结果。
- 稳定性复测只处理本轮通过前置检查的候选。
- 所有查询、写入和测试统一限定当前 `run_id`。

### 第4批：完整主流程调度和恢复

- 主流程是唯一调度器。
- 每阶段定义输入、输出、成功、空结果、失败、超时、有限重试和恢复规则。
- 已完成阶段恢复时跳过；未完成阶段安全续跑。
- 不重新采集已完成来源，不改变已冻结名单。
- 不能安全恢复就停止，不另建任务冒充恢复。

### 第5批：网络出口身份与发布

- 如实区分云端、国内真实IPv4、福建移动真实家庭网络。
- 无真实家庭网络验证条件就标记未验证。
- 将发布审核、临时文件校验、原子替换、备份和发布记录接入唯一主流程。
- 发布失败必须保留上一版订阅。

### 第6批：精简清理与全仓库测试

- 删除确认废弃的迁移代码、迁移测试和重复说明。
- 合并重复工具函数和重复配置，但不制造新的平行框架。
- 清理未使用依赖、空目录和过时文档。
- 保留必要测试，补足单元、集成、恢复、发布失败保护测试。
- 运行全仓库测试；未通过先修复，不进入验收。

### 第7批：整体验收

按 `docs/CORE_FLOW.md` 完整执行端到端流程，覆盖正常、零候选、候选上限、多频道同线路、来源重复、超时、中断恢复、阶段失败、网络身份未验证、发布失败和上一版保护。

只有所有验收项均有实际证据，才可宣布完成。

## 四、文件治理规则

| 文件 | 管理规则 |
|---|---|
| `docs/CORE_FLOW.md` | 唯一业务施工图，业务规则只在这里维护 |
| `docs/MASTER_PLAN.md` | 施工批次、文件治理、进度、验收 |
| `README.md` | 简介、安装/启动方式、链接到施工图 |
| `config.yaml` | 唯一运行参数来源，不在代码重复硬编码业务上限 |
| `config/channels.yaml` | 唯一38频道来源 |
| `iptv_auto/pipeline.py` | 唯一业务入口，不复制业务实现 |
| `iptv_auto/database.py` | 唯一数据库schema和初始化 |
| `tests/` | 只保留当前V3行为测试，不保留旧迁移测试 |
| `.github/workflows/iptv-auto.yml` | 只做环境准备、测试、数据库持久化和启动主程序 |

任何文件删除前必须完成引用扫描，并确认没有动态导入、配置路径、workflow或测试引用。

## 五、代码施工与交付规则

1. 先读取GitHub `main` 分支真实文件，再修改。
2. 先核对上下游接口和数据库结构，不按单个文件孤立修改。
3. 一批相关文件必须成套准备，不能先让用户上传不完整接口。
4. 交付完整文件，不要求用户手工拼接代码。
5. 每个文件提供准确仓库路径。
6. 给出简短GitHub网页操作步骤和提交说明。
7. 本地能运行的测试必须先运行；说明实际命令和结果。
8. GitHub Actions结果只证明该次实际执行的步骤；`test_only`不等于正式pipeline验收。
9. 未实际运行、未实际提交、未真实发布，不得声称完成。
10. 用户没有明确授权时，不执行GitHub写操作。

## 六、测试分层

- 数据库测试：新库初始化、表/索引/约束、外键、结构不匹配拒绝。
- 候选池测试：来源去重、多来源关系、全来源后排序、36配对上限、冻结不可变。
- 恢复测试：来源已完成不重抓、未完成来源续跑、已冻结名单不变、阶段已完成不重跑。
- 下游隔离测试：测量、评分、深度检测、内容检查、稳定性不得混入其他run或历史线路。
- 多频道测试：同一物理线路关联多个频道，线路级探测可复用，但频道内容结果分别保存。
- 发布测试：格式错误、频道错误、超数量、校验失败时上一版保持不变；成功时原子替换。
- 全仓库测试：真实主流程集成、零候选、超时、失败、恢复和运行报告。

## 八、最终验收原则

- 38频道目录正确且唯一。
- 一条主流程、一个入口、一套配置、一个数据库。
- 所有来源先完成采集，再公平筛选并冻结候选。
- 候选配对和物理线路统计口径清晰。
- 所有下游阶段只处理本轮冻结候选。
- 多频道配对不丢失、不串台。
- 阶段停止、交接、失败、超时和恢复真实有效。
- 新数据库跨GitHub Actions运行持续保存。
- 网络出口身份真实、准确。
- 正式发布有审核、原子替换和回滚保护。
- 不再存在旧迁移逻辑、重复流程和无引用文件。
- 全仓库测试和端到端验收通过。
- 定时运行只有在整体验收通过并得到用户明确确认后才允许启用。
